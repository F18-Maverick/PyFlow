# AGENTS.audit.md - 审计模式规则

本文件适用于 AI 编码代理（Agent）和人类审查者（Reviewer）。
目标：在 AI 大量生成代码的前提下，保证存量代码的**可审计性、问题可复现性和覆盖结论可验证**。

---

## 存量代码审计

审计是只读任务：Agent 不得在审计过程中修改代码。发现的问题另开修复任务，走增量流程。
主要增量流程在项目根目录下的 `AGENTS.md` 中有详细说明。

### 审计卡模板

```text
审计目标：这次要回答什么问题（例：加密是否覆盖所有传输路径）。
审计范围：模块/文件/执行路径，逐条列出。
风险假设：怀疑哪些地方有问题，为什么（例：控制层已加密，文件传输层可能仍是明文）。
审计维度：契约完整性、路径覆盖、旁路、错误处理、并发、日志脱敏、依赖。
证据要求：每个发现需要什么证据（文件:行号、调用链、抓包、测试结果）。
不审计范围：明确排除什么，避免范围蔓延。
输出格式：发现清单（每条含严重度、位置、证据、建议）+ 模块覆盖结论（每个模块：有问题 / 无问题 / 未审计及原因）。
```

### 审计计划

1. 切片方案：按模块/风险把审计范围分成若干片，每片预估工作量
2. 每片的审计方法：静态分析列调用点 / 契约提取 / 路径枚举 / 代码走查
3. 每片预期产出
4. 明确不审计的范围

### 审计发现分级

- **P0 全局属性失效**：安全旁路、鉴权遗漏、明文泄露、日志泄露密钥；
- **P1 结构性缺陷**：绕过统一入口、重复实现、错误处理缺失、并发隐患；
- **P2 可维护性问题**：命名、重复代码、缺注释；
- **P3 建议**：优化项，不阻塞。

每条发现必须含：严重度、文件:行号、调用链或数据流、证据、建议修复方向。没有位置和证据的发现视为无效。

### 审计验收

- 审计范围内每个模块都有结论（有问题 / 无问题 / 未审计及原因）；
- 每条 P0/P1 发现可被人独立复现；
- 明确列出未审计范围和原因；
- 不接受“通读了，看起来没问题”作为结论。

### 审计后的处置

- P0/P1 发现转为修复任务，走 `AGENTS.md` 增量流程（需求卡 → 计划 → 原子提交 → 验收）；
- 审计发现转化为静态检查、测试或 `AGENTS.md` 规则，防止回归；
- P2/P3 记录到技术债清单，不阻塞。
