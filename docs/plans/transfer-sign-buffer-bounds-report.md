# 传输协议缓存有界化：实施与验收报告

状态：按最终“达到 64 KiB 即扫描、批量清理”语义完成实现与验收；阈值清理版受影响集 **118 passed in 328.93s**，Python 3.10 完整回归 **685 passed in 528.50s**。完整短行累计至上限不会报错；只有单条未终止行自身达到 64 KiB 才失败。未创建 git 提交、未合并、未推送，待人工最终审查。

## 1. 需求与实施边界

用户先要求消费后删除与 64 KiB 上限，随后明确容量到达时应主动扫描全部完整协议行并批量清理，不应因短行聚合达到容量失败。最终实现遵循此语义：达到阈值锁内扫描、保存 start/ACK/error 状态、删除记录并继续解析；单条无法分界的超长行才走失败关闭。不使用产品 `threading.Event`，不改 ACK 时机、超时或正文路径。

## 2. B1：直传消费后删除

### 实现

`PyFlow/network_api/connect_tcp.py` 中，原 `_take_wire_lines` 与两端完整 sign 历史统一迁移到私有 `_TransferSignBuffer`；没有保留旧辅助函数或兼容入口。

- `feed` 按 TCP byte stream 分段、逐行解析，完整行才 UTF-8 解码/strip；单次读取大于 64 KiB 时分窗口，不先建立任意大的历史拼接串。
- 原始完整线长（含换行）在解码/strip 前入账；空行直接消费。`pending_bytes + len(partial)` 不超过 65,536。
- 完整行入队使窗口达到 64 KiB 时，接收线程持锁核对所有完整行，锁存 start/ACK/error，再一次删除整段并释放配额，然后继续当前输入。添加一行会越界时先扫描已有完整行再添加。
- 消费线程的 `consume()` 在相同锁内扫描未满批次并返回 marker 状态快照。producer 阈值扫描与调用线程阶段扫描都在判定后批量删除。
- 任意数量的合法短行按多个窗口扫描；**累计队列达到上限不会报错**。单条未终止行达到 64 KiB 时仍拒绝，因为不能安全清空半行后恢复解析。
- 正文阻塞期间 producer 可自扫描；固定 marker 识别结果跨阶段保留。接收/消费对标记和队列的操作使用同一局部锁，不增加 Event。
- header/未知行没有永久历史。socket/file I/O、暂停等待和关闭不在队列锁内执行。

### ACK/EOF 顺序

每轮等待先快照 `file_running`，再消费队列，最后使用该快照检查关闭状态。如果只按“消费空队列 → 读最新关闭状态”的顺序，接收线程可能刚好在两者之间提交 ACK 并关闭，导致误报失败。当前顺序保证：读到关闭快照时，之前提交的记录有机会被消费；读到运行快照时，稍后的关闭留到下一轮判断。

已完整 ACK 与随后 error/关闭的原有判定优先级未重新定义；未终止 ACK 仍不能成功。

## 3. B2：中继滚动窗口

`TCP_Server_Base._forward_read_sign` 保留现有字节子串 marker 匹配及 `bytes | None` 返回契约。

- 每个扫描窗口最多 65,536 字节；单次读取较大时分段扫描。
- 未匹配时只保留 `max(len(target), len(error)) - 1` 字节的后缀。默认 start 保留最多 36 字节，最终 ACK 保留最多 24 字节。
- 同一次读取必须扫描完再接受目标 marker；该读取后半段出现 error 仍按原有顺序拒绝，不能因内部窗口切分而让前半段 ACK 提前成功。
- deadline 不因扫描/清理而重新开始，socket timeout 在出口恢复。无法在有界窗口内表示的超长目标 marker 直接返回 `None`，避免非前进循环；既有固定 marker 均远小于上限。
- 目标只有真实最终 ACK 才标记完成；全目标门槛、上游换行 ACK、写成功才删除路由等规则不变。

## 5. 机械验证

### 修复前证据

本轮开始时在真实旧辅助函数上输入 65,536 个无换行字节：输出 `before: unterminated bytes retained = 65536`，容量不变量断言失败。说明不是仅按代码推断旧缓存无界。

### 定向回归

- 阈值清理语义下，`test_wire_lines.py`、resume、file transfer、crypto 四文件受影响集：**118 passed in 328.93s**。
- 结果包含两个方向真实 socket 在正文暂停时注入超过 64 KiB 的完整短行；producer 批量扫描后发送继续、正文相同、真实 ACK 成功、进度移除。两个方向注入单条无换行长行则失败并保留进度。
- Ruff 新增/重写 parser 单测 0 条、transfer integration 新代码无诊断；两个既有 10 秒等待处诊断及其他存量问题未因本次改动产生。

### 首轮全量失败与就绪修正

命令：

```sh
uv run --python 3.10 --with pytest --with flask pytest -q
```

首轮结果：**681 passed, 1 failed in 501.18s**。失败为 `test_client_uploads_multiple_files_to_destination`：只等 `one.bin`/`two.bin` 存在，就检查内容；实际 `one.bin` 为 `b''` 而非 `b'one'`。接收端在正文写入之前就会创建文件，因此 exists 不是完成条件，测试相邻用例已经使用 `wait_for_text`。

局部修正仅把两个 exists 等待换成等待准确文本内容，保留 `read_bytes() == b"one"` 和 `read_bytes() == b"two"`。独立进程真实调用 `/multiple_file` 后，两个内容等待和两个原始 bytes 断言均通过。没有为此改动产品传输行为、删用例、加 sleep 或放宽断言。

历史记录：旧语义版本在就绪等待修正后为 **682 passed in 518.92s**；它发生在需求方澄清“容量到达应批量清理”之前，不属于当前最终实现验收。

最终阈值清理语义的完整回归：

```sh
uv run --python 3.10 --with pytest --with flask pytest -q
```

结果：**685 passed in 528.50s**，无失败、无跳过。

### 强制 ACK/EOF 消费竞态

独立实际文件上传在最终等待中人为安排：消费线程先检查空队列，随后接收线程收到 ACK 并进入关闭，再允许消费线程继续。本轮 **110,000 字节**正文相同，发送返回 `True`，上传记录移除，验证运行状态快照不会把“旧空队列 + 新关闭”误判为失败。用于安排顺序的 Event 仅在临时烟测进程中使用，产品没有新增 Event。

## 7. 风险、未覆盖与交付闸门

- Windows/macOS 与 free-threaded Python 未在本轮实际运行；没有声称平台 CI 或所有解释器已验收。
- 64 KiB 是原始协议行/未消费配额或中继扫描窗口限制，不是整条连接、Python 堆、socket 缓冲、加密帧或文件正文总内存限制。
- CPU/连接数限流、其他协议入口和全局安全属性不在本轮范围。中继仍沿用既有字节子串匹配，没有冒称已切换为严格整行认证。
- TCP 写成功但 ACK 实际未到达、断网、原有最终等待超时等仍按既有失败/续传规则处理；未增加重试、ACK-of-ACK、drain、shutdown 握手或延迟关闭。
- 完整短行达到一个或多个 64 KiB 批次时会自动 scan/clear 后继续，不会因聚合积满退出。只有单条无法分界的超长行拒绝并保留恢复记录；大于 64 KiB 的正文成功传输仍有覆盖。
- 临时烟测均为进程内脚本字符串和 `TemporaryDirectory`，未在仓库留下脚本或测试数据。永久规则沉淀为边界/消费删除/中继错误顺序测试与运行文档。
- 阈值清理语义的全量验证已通过：**685 passed in 528.50s**。人工最终审查、跨平台证据和平台 CI 仍是剩余交付闸门；未提交、未合并或推送。
