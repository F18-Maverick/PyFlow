# 原生 TCP 一对一文件转发 — 需求卡

状态：**需求方已确认本卡，仅授权编写[更改计划](forward-one-to-one-plan.md)，未批准实施**。沿用[文件转发词汇表](../../GLOSSARY.md)。

## 已明确的目标

- 在发送端 `TCP_Client_Base` 新增可选参数 `is_forward_one_to_one=False`，现有调用保持共享上行拓扑、控制和交付语义。同一条目向多个目标仍只上传一份，用户暂停/继续仍作用于整个转发任务。
- 开启时，由发送端将同一条目的多目标请求拆为逐目标的单目标转发。已获准使用资源的任务可并行传输；不得等前一个目标传完整个文件才启动下一个。B 的用户暂停或继续不改变 C 的用户暂停状态。
- Q3 已选：并发单位是「文件条目 × 去重后的目标」，不是每个目标一条串行文件队列。x、y 同时发往 B、C 会产生四个单目标任务；即便 x→B 正暂停，只要有名额，y→B 也可开始。
- Q4 已选：开启模式的发送端复用现有 `max_thread_num`/文件发送名额，与同一实例内已受该限制的普通批量发送共同限流；多次转发命令不各自乘一份额度。满额等待，不提前开数据连接、占数据端口或给每个等待项都起线程；活跃但暂停的任务不释放仍在占用的资源和名额。
- Q5 已选：同一新模式命令中，若可从请求判定两个条目会写同一目标的同一目的路径，则保留第一次、跳过后者并给可定位提示；不更名、不并发写同一路径。不同目标或不同相对目录不构成此冲突。
- Q6 已选：没有命令级父任务、总进度或整批 ACK。每个获准单目标任务沿用自己的 upstream FID、child FID、进度、用户控制和最终确认；B 的成功清理不能删除 C 的失败/恢复依据。已有公开入口的返回值、查询和五字段进度格式不改。
- Q7 澄清已选：排队项仅属于提交命令时的实际控制会话；未调度不分 FID、不开数据端口、不建进度行、不持久化。旧会话结束就取消尚未发起的项并提示，不能借用重连后的 socket；不自动重发等待项。已在途的中断传输走既有进度恢复。
- Q8 已选：获准进入既有单目标握手即按在途处理，可在首条 `/forward_item` 发出前绑定 FID 和已有五字段上传行（跟踪关闭不新建行）。不要因没有正文或握手结果不确定而删掉已成立任务的恢复依据。只拆首次请求，不因重连或构造参数变化重新拆分历史 route。
- Server 不接收新的模式参数或模式标记。交给它的仍是既有单目标或多目标转发请求；不另造一套文件传输协议。
- 沿用原生流式转发的资源保护、控制会话、握手与真实收件确认，不用取消背压或提前报成功换取独立性。

## 范围与数据边界

- 范围是 `PyFlow/network_api/connect_tcp.py` 的原生 `/forward_file`、`/forward_folder`（文件夹内实际文件）和共用入口，包括现有 Web 单目标调用；不扩展 Web 选目标界面。构造参数置于现有可选参数末尾；普通配置沿用 Client 构造入口，不新增线上字段。
- 原生转发不在 Server 落文件；不绕过统一控制消息和文件数据加密路径，不新增文件正文、密钥或完整负载日志。普通直传、消息转发、独立落盘扩展均不是本次新数据通路。
- 不改 CI、依赖、覆盖率策略；不删或弱化既有测试。风险较高的部分是多任务并存时的资源计账、传输身份和清理。
- 不承诺不同进程/发送者在接收盘上的写路径互斥、远端文件系统别名识别、源文件传输中变更的快照一致性、进程内存硬限或带宽公平。不会把 Server 的普通文件发送名额说成现存的原生中转任务数上限。

## 资源口径：配置值、计账范围、实际用量分开

现有[传输说明](../source/File_Transfer/File_Transfer.rst)和 `_forward_pump` 的实现是每次中转各有队列计数，允许一次入队超出水位；这既不是预分配，也不是进程 RAM 上限。

Q1 澄清和 Q2 已确认：同一 Server 实例中所有并发原生转发（不同文件、目标、命令或源端，含旧模式）共用既有 `max_mem_buff` **一份严格的待下发字节额度**。例如 64 MiB 已由 x→B 用满，即使 y→C 的队列为空，也须等待有足够额度才入队。不乘大配置值、不预分配、不跨任务共享正文；只协调计账、等待和释放。用户暂停/继续只改变所属任务状态，不能越过资源等待。Server 因此要改通用背压，不增模式参数。

| 路径 | 必须实际观察的结果 |
|---|---|
| P1 默认、显式 False、原本就只有一个目标 | 同一文件的默认多目标仍只有一次上行、一个原任务；全部已接受目标真实 ACK 才收尾。单目标复用原握手，无模式字段。 |
| P2 输入和落点：原生文件/目录、多条目、目标列表、destination、Web 既有入口 | 引号/空格和嵌套相对目录保留；重复目标只交付一次，自己不分 FID，不同端口的合法目标照常；同命令目的路径冲突跳过后者。不可达/Server 目标及无效文件不妨碍其他项。 |
| P3 一对一命令、多个文件/目标、并发名额 | x、y 发 B、C 是四个独立任务；受限时不超同一 Client 现有名额。阻住 x→B 的正文或 ACK 后 C 能完成，有空位时 y→B 不等 x→B。未调度不占数据端口/进度行。 |
| P4 用户暂停与继续 | 源端、Server、目标端仍沿原 FID 和角色路由，由源端仲裁；B 的暂停/继续不改变独立 C 的状态，同一 B 数据连接可继续。在途字节可排空。False 模式按原任务联动。 |
| P5 Server 内存预算 | 同一 Server 上来自不同请求/源的单目标、多目标及恢复并存时，所有排队／writer 未交付的计费字节之和始终不超过额度。块大于预算、扇出大于预算、元信息、慢 writer、失败/取消/停止都要有界、有进展、最终归零；自动背压不发用户控制。 |
| P6 错误、握手和控制会话更替 | 乱序端口、单项协商拒绝或数据失败不串 FID、不取消健康任务；旧会话的等待项撤销、已准入 owner 收尾，不能借新 socket。用户手动关闭同样释放等待和名额。 |
| P7 真实交付与恢复 | B 完成只清 B；C 中断/重连按原 upstream/child FID、实际文件 offset 和原路径重放。空文件、offset=0/EOF、最终 ACK 丢失沿既有规则；跟踪关闭不伪造持久进度；旧多目标 route 不迁移成多条新 route。 |
| P8 环境和回归 | 明文/加密、线程/异步 Server、系统端口/手动端口生命周期；普通直传、消息、落盘扩展不进入新分支。检查临时连接/端口、线程、路由、预算归属和真实内容，不以文件存在或一次 pytest 通过代替证据。 |
