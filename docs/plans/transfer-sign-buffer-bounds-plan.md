# 传输协议标记缓存有界化：消费后删除版方案

状态：需求方已明确“审计完成，开始更改”。B1/B2 已实施并完成定向测试与隔离运行烟测；最终验收结果与差异见 [transfer-sign-buffer-bounds-report.md](transfer-sign-buffer-bounds-report.md)。未创建 git 提交、未合并、未推送，人工最终放行与平台 CI 尚未发生。不使用 `threading.Event`。

## 1. 需求卡

### 目标

- 直传发送端的完整协议行进入有界待处理队列；消费线程记录已处理前缀，处理后删除，不保留完整行历史。
- 未终止协议行同样有长度上限，不能通过一直不发送换行让 `partial` 累积增长。
- 中继等待 start/final ACK 时不再无限累积 `buf`。
- 保留此前修复的粘包、拆包及 ACK 后紧随 EOF 的行为；必须先取得判定结果再删除记录，不能因索引前移或连接关闭而跳过已入队 ACK。
- 不使用 `threading.Event`，不增加线程或新的握手。

### 非目标与禁止项

- 不更改文件正文、文件元信息的二进制收发、文件分块大小、FID、进度模型或续传匹配。
- 不更改 ACK 发送时机、既有等待时限、接收端关闭时机、加密握手或统一 send/receive 入口。
- 不删除/跳过既有测试、不弱化断言、不增加 lint 忽略、不改 CI、依赖或覆盖率。
- 不将“达到容量就清除”实现成无条件丢弃半条协议行或已识别状态。
- 不把 `max_dict_size` 或 `file_transfer_chunk_len` 当成协议缓存上限：它们不是同一个契约。
- 不声称整条连接或 Python 进程总占用小于 64 KiB。协议原始字节、待处理记录的线长配额受限；Python 字符串/容器、接收对象、加密层和文件缓冲仍有额外占用。

### 数据与安全边界

本方案只读取发送端入站的协议标记，不对正文执行分行或 strip。完整行最多暂存至下一次容量扫描，不新增原始内容日志。达到 64 KiB 时扫描并批量清理完整记录、保留 start/ACK/error 判定，然后继续解析后续字节；不能截断后把尾部误识别成新命令，也不能丢弃已识别 ACK。

风险等级：中。缓存回收影响 start/ACK/error 的可见性；误清理可能把成功传输误判为失败，错误识别成功则会破坏进度恢复。

## 2. 64 KiB 的准确含义

设内部常量 `TRANSFER_SIGN_BUFFER_LIMIT = 64 * 1024`，不是公共配置项。

- **批处理窗口上限**：每个扫描窗口的原始协议字节最多 65,536 字节。一次读取更大时分段处理，不先拼成更大的历史缓冲。
- **直传单行上限**：一条协议行连同结尾的 `\n` 最多 65,536 字节。单条未终止行耗尽此上限时无法识别行边界，按既有失败关闭路径处理。
- **直传待处理总量上限**：未扫描记录的原始线长之和，加上尚未终止的 `partial`，不超过 65,536 字节；在 strip/解码前按 bytes 计量。
- **达到容量时**：处理完当前完整行后若总量达到 65,536 字节，立即扫描队列全部记录、保存识别结果、一次删除已扫描前缀并释放队列配额，再继续处理同一次读取的剩余数据。若追加一条完整行会越过上限，则先扫描/清空已有完整行，再追加该行。
- **partial 占满可用配额时**：先扫描并清除已有完整行，保留 partial；如果 partial 本身达到 65,536 字节仍无换行，则它是一条超长协议行，走失败关闭。不会清掉半条行继续寻找伪造的后缀命令。
- **及时检查**：每次读取后解析完整行，不等缓冲填满；容量扫描与调用线程正常消费走同一套锁内 marker 核对/前缀删除逻辑。
- **无错误的正常聚合**：任意多条各自合法的短行即使单次读取累计超过 64 KiB，也分批扫描并继续；队列字节配额满本身不是传输错误。超限失败只针对单条未终止协议行，或无法安全分界的单条超长行。

64 KiB 是待扫描记录与 partial 的并存窗口上限，不是允许队列增长后失败的阈值。每到上限扫描完整记录、保存识别结果并批量清理；只有无法分割的超长单行不能通过清队列解决。

## 3. 直传设计：有界队列、消费索引与前缀删除

修改两端 `file_transfer_mode` 中的协议接收线程及 `_take_wire_lines`。

### 3.1 原始字节与临时行

1. 输入继续来自现有 `receive_message`，加密数据先经原有解密路径。
2. 按窗口剩余空间分段扫描 `\n`，在分配/追加之前检查容量；完整行才 UTF-8 解码，沿用既有 strip/空行处理，不改文件内容路径。
3. 完整非空行连同原始线长进入临时待处理队列；队列达到 64 KiB 时扫描所有记录、锁内保存识别结果后批量删除，不保留完整行历史。空行直接消费。
4. 队列与 partial 的线长在锁内核算。若部分行占用剩余空间，先扫描/释放已有完整记录，再保留 partial。
5. 合法完整短行达到批次上限时不报错、不丢行，扫描后继续当前读取。只有单条行自身超限(未终止尾部达到 64 KiB，或换行位置已超过单行上限)才走既有失败路径；不截断、不重同步到行内后缀。
6. EOF 不当作换行，不把未终止 ACK 提交为成功；EOF/关闭不清空已排队记录。

实施落点：原 `_take_wire_lines` 的两处产品调用及边界测试统一迁移到私有 `_TransferSignBuffer`。`feed` 逐行解析，达到 64 KiB 时调用锁内扫描逻辑将完整 pending 前缀批量核对、锁存 marker 并删除；`consume` 在阶段检查时对未满批次执行相同操作。两者共用队列、线长配额和结果锁，没有保留旧辅助函数或适配入口，公开 API 不变。

### 3.2 一个生产者、一个消费者

- 接收线程是唯一生产者，负责解析与入队。
- `file_transfer_mode` 调用线程负责阶段性消费；接收线程在达到容量时也调用同一锁内扫描/清理逻辑。
- 批量扫描维护的 start/ACK/error 结果字段由两侧仅在同一把锁内读写；不依赖某个线程私有的共享状态。
- 读取 marker 结果也通过同一锁快照；不使用 `threading.Event`，不增加线程或结果通道。
- 接收线程发现本次输入含 error sign 后，在锁外走现有关闭路径；已扫描记录中的 error 状态仍保留，调用线程在 EOF 后消费快照。
- 完整行队列达到上限时批量扫描并删除，不是错误。只有单条无法以 `\n` 安全分界的超长协议行沿用接收失败路径；发送端仍消费已入队记录再检查关闭，不改变 ACK/error 既有优先级。

### 3.3 索引与删除规则

1. 每次消费时，在锁内取得当前队列长度，`read_index` 从零开始核对这一批。
2. 对当前行先完成判定：start/ACK/error 更新本次调用的固定结果；header 和未知完整行按既有语义忽略。
3. 只有判定完成才增加 `processed_count`，并累加对应的已消费原始线长。
4. 本批核对结束，执行一次 `del pending[:processed_count]`，同时扣减配额，再释放锁。结果先保存，原记录后删除。
5. 下一批索引重新从零开始，不跨删除操作保留旧下标。新追加的记录只会在锁释放后入队，不会被上一批的前缀删除误删。

这是“处理过的记录不进入下一批”的消费删除，与处理一条就删除一条具有相同的回收语义，但避免每次删列表头都移动后续全部元素。不能在 `enumerate(pending)` 中 `del pending[index]` 后继续递增：列表左移会跳过下一项。

### 3.4 处理完成的含义与阶段衔接

- 每条记录先判定并更新固定结果，再删除；“已经遍历过”不等于处理完成。
- 同一批出现 header 和 ACK，两条都核对并删除，ACK 结果保留。容量触发的 producer scan 与发送线程 consume 共用同一锁和扫描逻辑；每轮等待仍先快照 `file_running` 再消费，然后依据锁内 marker 快照处理关闭。
- 队列达到 64 KiB 时立即扫描/清理；在启动等待、正文分块发送前及最终 ACK 等待处也可主动消费部分批次。阶段切换不重置判定结果。

核对并发时需要区分：生产者单纯 append 不会移动旧记录的下标；下标前移来自删除自身。锁保护的是“核对、发布结果、删除、更新配额”这一组操作，不能把 CPython 某个单独 list 操作的原子性当成整组操作的保证。

## 4. 中继设计：扫描后仅保留跨边界匹配所需后缀

修改 `TCP_Server_Base._forward_read_sign`；其调用点是目标连接的 start 等待和 writer 的最终 ACK 等待。

- 输入仍经 `receive_message`，返回仍为 `target bytes | None`。
- 沿用当前字节标记查找语义；本次不顺手改成“必须整行匹配”，也不额外要求 marker 自带换行。
- 扫描窗口最多 64 KiB。一次读更大时分段扫描；同一次读取内仍保留现有先判 error、再判目标的顺序。
- 未发现目标或 error 时，清除已扫描历史，只保留最后 `max(len(target), len(error)) - 1` 个字节。这已足够识别跨两次读取/窗口的 marker。
- deadline、超时设置/恢复、EOF/异常返回 `None` 均保持不变。窗口清理不重置 deadline。
- 中继不是按行解析器，因此这里限制的是等待标记时保留的历史窗口，不额外引入超长行拒绝规则。错误标记和目标标记的跨边界匹配都必须回归。

目标 writer 只有收到真实最终 ACK 才完成对应路由；全目标完成门槛、上游 ACK 换行发送以及 ACK 写成功才删除路由的规则均不变。

## 5. 数据流与路径全集

直传：协议入站 bytes → 有界分行/配额检查 → 待处理队列 → 调用线程核对并保存固定结果 → 按已消费索引删除前缀/释放配额 → 原有等待与进度处理。

中继：目标入站 bytes → 有界窗口查找 error/target → 匹配则返回 → 否则只留短后缀 → 原有路由完成/失败处理。

| 路径 | 修改点 | 必须保留的行为与验收 |
|---|---|---|
| 客户端上传普通文件 | 客户端 `file_transfer_mode` 接收线程 | 初传、拆包/粘包 ACK 返回成功，正文相同、上传进度清理 |
| 服务端下发普通文件 | 服务端 `file_transfer_mode` 接收线程 | 同上，覆盖相反方向 |
| 文件夹项 | 两端相同发送腿 | 相对目录及正文不变，失败仍保留进度 |
| 双向续传与 EOF 重放 | 两端相同发送腿 | offset=0、部分 offset、offset=total；header/ACK 同批仍成功 |
| 双向公钥推送 | 两端同一发送函数 | 无进度的 plaintext 公钥腿仍完成，原有 TOFU/握手不变 |
| 直传 error/EOF/单条超长行 | 两端协议接收线程与消费点 | 容量批次扫描后保留错误状态；完整 ACK 不丢；只有无边界超长行失败，不清理恢复记录 |
| 中继目标 start | `_forward_read_sign` 的 start 调用 | 目标/error 跨读取和跨窗口仍可识别，失败沿用跳过/清理路径 |
| 中继目标最终 ACK | writer 的 `_forward_read_sign` 调用 | 真实 ACK 才完成目标，全目标聚合和上游路由删除门槛不变 |
| 中继错误/超时/断开 | 同上两处调用 | 返回 `None`，deadline 不被持续数据延长，未确认目标不标完成 |
| plaintext/encrypted | 两端协议读取和中继入口 | 不绕过现有接收/解密；正常发送结果与落盘内容相同 |

## 8. 验收证据要求（实施结果见报告）

### 边界与状态契约

- 小于 64 KiB 的正常 start/ACK 立即解析，不为凑窗口而等待。
- 大量完整短行累计达到或超过多个 64 KiB 批次时均被扫描并批量清理，后续有效 ACK 仍成功，不因聚合容量报错。
- ACK 被容量触发的 producer scan 清理后，调用线程仍读取到已锁存结果；ACK 与 header 同读、ACK 后 EOF、调用线程晚于接收线程关闭均不丢确认。
- 65,535 字节内容加换行的单行边界可接受；单条未终止行达到 65,536 字节被拒绝。单次读取包含多个合法短行且总量超过 64 KiB 时持续分批处理。
- 单条超长行内部藏有 ACK 时不得把后缀重同步成有效 ACK；未终止 ACK 不提前成功。
- 中继 target 与 error 跨窗口仍识别；持续噪声期间缓存不随累计输入增长、总等待时间不重置。

## 10. 本轮独立验证（不是产品修改后的验收）

在 Python 3.10.20 运行的独立原型记录了算法风险，均不是最终产品验收：

- 对 `[HEADER, ACK, ERROR]` 使用 `enumerate` 并原位 `del[index]`，实际只访问 HEADER、ERROR，ACK 留在列表中，确认索引前移会漏处理。
- 核对 `[HEADER, ACK]` 后前缀删除：消费两项，队列清空，局部 `ack_seen` 保留为 True。
- 控制生产者与消费者交错：消费者持锁核对并删除一项 header，生产者随后追加 ACK；下一批正确消费 ACK，没有跳项或误删。原型中的 Event 仅用于安排验证时序，不属于产品设计。
- 早期原型曾在 64 KiB 聚合容量满时拒绝下一条短行；需求方澄清后此规则已被实现层的“扫描全部完整行、保存结果、批量删除并继续”取代，不能作为当前验收结论。
- 中继滚动窗口原型对 start 的 36 个切分点、ACK 的 24 个切分点，以及 error 跨界/同次读取目标后出现 error 的情况均验证通过；窗口 65,536 字节，后缀不超过 36/24 字节。最终产品证据见实施报告。
